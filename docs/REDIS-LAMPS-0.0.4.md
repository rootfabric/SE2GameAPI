# SE2 Redis Bridge 0.0.4

Рабочая связь Python → Redis → плагин SE2 → светильник → подтверждение.
Проверено на сохранённом творческом мире: три Interior Light 0.5 m на Concordia Research Station.

## Запуск

1. Запустить Docker Desktop и локальный Redis:

```powershell
docker start se2-redis-bridge
```

При первой установке контейнера:

```powershell
docker run -d --name se2-redis-bridge -p 127.0.0.1:6379:6379 redis:7.4-alpine redis-server --appendonly no --save ""
```

2. Закрыть игру обычным способом после сохранения, затем из этой папки:

```powershell
.\start-smoke.ps1 -ContinueGame
```

3. Использовать secontrol из локального checkout (ветка `codex/se2-lamp-bridge`):

```powershell
$env:PYTHONPATH = 'C:\secontrol\src'
python .\examples\redis_lamp.py --cycles 3
```

Пример мигает тремя выбранными лампами, затем восстанавливает исходные состояния. Постоянного автоматического мигания при запуске плагина нет. Старый `blink.json` не используется.

## Python API

```python
from secontrol.se2 import Client

with Client() as client:
    lamps = client.lamps(grid_name="Concordia Research Station", name="Interior Light 0.5 m")
    lamp = lamps[0]
    result = lamp.disable()
    assert result.status == "confirmed"
    assert result.actual_state["enabled"] is False
    lamp.enable()
    lamp.toggle()
    lamp.set_enabled(True)
    state = lamp.refresh()
```

`secontrol.se2` — отдельный opt-in backend, без изменений старых классов и Redis-протокола SE1. Методы возвращают `CommandResult`, а не число подписчиков. Поддерживается `switch.enabled`; цвет, радиус и яркость ещё не реализованы. Телеметрия содержит Enabled, Working, Functional, имя, грид и revision. `refresh()` получает последний опубликованный снимок; немедленное состояние после команды берите из её ACK.

## Нагрузка на игру

- Таймер 20 Гц ставит максимум одно ожидающее действие в очередь приложения; сценовая работа тоже не накапливается.
- В потоке серверной сцены: поиск по реестру, чтение/запись свойств и подтверждение на следующем проходе.
- Командный проход: максимум 8 команд и мягкий бюджет 0,5 мс. Нельзя прервать уже начавшийся вызов игрового API.
- Одновременные команды к одной лампе разделены подтверждением; старый ACK не выдаётся за результат следующей команды.
- Телеметрия снимается порциями до 64 ламп с тем же мягким бюджетом. Публикуется завершённый снимок; при нагрузке его частота снижается.
- Реестр обновляется через запрос только LightComponent раз в 5 секунд. Это отдельная синхронная операция, не имеющая жёсткой гарантии 0,5 мс; её время измеряется как discoveryMs. Полных обходов блоков мира на каждую команду нет.
- JSON, Redis и запись диагностического файла работают в фоновом потоке. Один общий ConnectionMultiplexer, автоматическое восстановление соединения.
- Очередь клиента ограничена 256 сообщениями атомарным Lua-скриптом; в плагине максимум 64 незавершённые работы. Кооперативные клиенты обязаны соблюдать этот протокол.
- Старые GridDiscovery и LightBlinker сохранены в исходниках как прототипы, но НЕ создаются и не выполняются.

## Протокол и гарантии

- `se2:local:state`: снимок и метрики, TTL 3 секунды. Проверять state=READY и sampledAtMs; присутствие Redis-ключа само по себе не подтверждает свежесть игрового состояния.
- `se2:local:commands`: ограниченная клиентом FIFO-очередь, TTL 15 секунд.
- `se2:local:reply:<requestId>`: результат, TTL 60 секунд.
- Поля команды: requestId (UUID hex), epoch, gridId, deviceId, cmd, expiresAtMs, опционально enabled и expectedRevision.
- Доступные команды: enable, disable, set_enabled, toggle.
- Подтверждение `confirmed` выдаётся после повторного чтения Enabled на следующем сценовом проходе. Working сообщается отдельно: включённая лампа без питания может не светить.
- Проверяются сессия, срок команды, принадлежность гриду, существование устройства и optional revision. Повтор одного requestId не выполняет toggle заново: кэш 60 секунд, допустимая жизнь новой команды до 10 секунд.
- Очередь Redis использует LPOP: при аварии между извлечением/исполнением и ответом результат может быть неизвестен. Это НЕ exactly-once и НЕ долговечная очередь задач. Клиент не повторяет toggle автоматически. При тайм-ауте перечитать телеметрию; после смены epoch заново найти устройства.
- Идентификаторы устройств действуют только в пределах epoch. Удалённые объекты проверяются через Scene.IsEntityAlive до доступа.

Сейчас это доверенный локальный стенд: Redis привязан к 127.0.0.1, endpoint плагина фиксирован. Общего сетевого API, авторизации игроков, leases и распределённого supervisor пока нет. Не публиковать этот Redis в общую сеть. Разрешение конкурирующих программ сейчас — порядок очереди и optional revision, а не владение устройством.

## Проверка 2026-11-09

[Машинный отчёт](docs/redis-lamp-test-2026-11-09.json).

- 12 переключений: подтверждены и Enabled, и Working.
- Повтор toggle трижды: одно переключение.
- Старый epoch, просроченная команда, неверные ID/грид, неизвестная команда и конфликт revision отклонены.
- 219 остальных ламп сохранили Enabled. Всего в мире 222 светильника; управляемые три выбраны явно.
- Redis остановлен и запущен: та же игровая сессия продолжила работу, новая команда подтверждена после reconnect.
- После тестов исходные состояния трёх ламп восстановлены.

| Режим | Среднее время сценового прохода | p95 времени прохода | Задержка ACK |
|---|---:|---:|---:|
| Без команд, 5 секунд | 0,029 мс | ≤0,1 мс | — |
| 12 клиентов, 96 команд | 0,045 мс | ≤0,1 мс | медиана 203 мс; p95 250 мс |
| 100 клиентов, 100 команд | 0,037 мс | ≤0,1 мс | p95 2281 мс |
| Один клиент | — | — | медиана 94 мс; максимум 110 мс |

100 клиентов управляют всего тремя лампами: очередь сохраняет порядок и растёт задержка, а не объём работы одного игрового прохода. Это короткие проверки на текущем мире, не доказательство работы на произвольном большом сервере. Максимум с начальной загрузкой/JIT — 5,0205 мс. Замер охватывает тело сценового callback; не является прямым сравнением FPS с отключённым плагином и не включает все расходы движка, сети, GC и репликации.

Python: 8 новых тестов и 3 теста SE1 rebind прошли. Ещё 4 существующих test_grid_blocks падают из-за отсутствующих get_block/paint_blocks; те же 4 падения воспроизведены на чистом архиве HEAD до изменений.

## Диагностика

Текущий снимок: `%LOCALAPPDATA%\SE2GameAPI\bridge-state.json`.
Ошибки транспорта: `%LOCALAPPDATA%\SE2GameAPI\transport.log`.
Сборка: `artifacts/plugin/`, загрузка: `artifacts/tools/Pulsar/Modern/Local/SE2GameAPI/plugin.dll` с зависимостями рядом.

```powershell
$env:PYTHONPATH = 'C:\secontrol\src'
python .\tests\live_redis_lamps.py
```

Этот интеграционный тест реально переключает три тестовые лампы и кратко перезапускает выделенный контейнер Redis. В finally восстанавливает их состояния. Старые PowerShell-тесты файлового прототипа относятся к 0.0.1–0.0.3 и для этой версии не используются. История прототипа: [DIAGNOSTICS-0.0.3.md](docs/DIAGNOSTICS-0.0.3.md).
