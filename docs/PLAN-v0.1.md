# План разработки SE2 Redis Bridge v0.1

Цель первой версии — получить работающий аналог вашего плагина для Space Engineers 1, но на движке Space Engineers 2.

Никаких программируемых блоков внутри игры, редакторов Python и новых игровых устройств. Плагин работает непосредственно с объектами игры, публикует телеметрию в Redis и принимает команды из Python.

Рекомендую начать с двух функций: гриды + светильники

## 1. Архитектура

Space Engineers 2 — VRAGE3

Гриды, блоки, реальные состояния устройств

Внутренний API движка

SE2 Redis Bridge — C# / .NET 10

Плагин Pulsar Modern

Обнаружение гридов, управление блоками, телеметрия

Redis: JSON, ключи состояния, Pub/Sub

Redis

Состояния, команды, подтверждения

Python

secontrol / Python-агенты

Скрипты управления, автоматизация, мониторинг

Базовый принцип: Python ничего не знает о внутренностях VRAGE3. Он видит стандартизированные гриды и устройства. При обновлении игры исправлять потребуется преимущественно C#-адаптер.

### Что переносим из первой игры

Я посмотрел исходники ваших проектов [SE-MessageBroker-Redis](https://github.com/rootfabric/SE-MessageBroker-Redis?utm_source=chatgpt.com) и [secontrol](https://github.com/rootfabric/secontrol?utm_source=chatgpt.com).

В `secontrol` уже реализованы нужные механизмы:

- Redis-каналы для получения состояний гридов и отправки команд.
- `Grid` и `Grids` для обнаружения объектов.
- `BaseDevice` для работы с устройствами.
- `LampDevice` с `enable()`, `disable()`, `toggle()`, чтением состояния и настройками светильника.

Мы сохраняем этот подход и формат Python-команд, насколько позволяет SE2. Старый C#-плагин не переносим напрямую: у VRAGE3 другая внутренняя архитектура и типы. Для новой игры потребуется отдельный слой доступа.

Первая версия ориентируется на одиночную игру или локальную сессию, где у плагина есть право изменять состояние мира. В настоящее время стандартная серверная инфраструктура SE2 ещё не эквивалентна SE1.&#x20;

## 3. Этапы разработки

P0. Исследовать внутренний API VRAGE3

Создать тестовый плагин из [шаблона SE2](https://github.com/CometWorks/client2-plugin-template?utm_source=chatgpt.com). Найти реальные классы игровой сессии, гридов, функциональных блоков и освещения. Установить, как получать идентификаторы и изменять состояние светильника.

Результат: плагин выводит в журнал список гридов и светильников, а также умеет включить один выбранный светильник без Redis.

P1. Реализовать обнаружение гридов

После загрузки мира получать список гридов, их имена, идентификаторы и список поддерживаемых устройств. Обрабатывать создание, удаление и переименование объектов. Начать с периодического сканирования, не усложняя первую версию подписками на все события движка.

Результат: актуальный список гридов и светильников в памяти плагина.

P2. Добавить Redis Gateway

Подключение к Redis, публикация списков гридов и состояний светильников, обработка входящих команд. Отдельный сетевой поток, ограниченная очередь команд и безопасное выполнение игровых операций в основном потоке движка.

Результат: внешний Python-скрипт может получать актуальные данные о мире.

P3. Управление светильниками

Обработчики `enable`, `disable`, `toggle`. Проверка существования блока и допустимости управления. После команды повторно прочитать состояние и отправить подтверждение в Redis.

Результат: светильник действительно загорается и гаснет по внешней команде, а Python видит результат.

P4. Совместимость с Python и приёмочные испытания

Добавить минимальный адаптер SE2 в `secontrol`, сохраняя существующий `LampDevice`. Проверить два грида, несколько светильников, перезапуск игры, пропадание Redis и восстановление соединения.

Результат: воспроизводимый тестовый сценарий, после которого v0.1 можно считать завершённой.

## 4. Предлагаемый Redis-протокол

Нужно сохранить привычную структуру SE1, но выделить отдельное пространство `se2`, чтобы две игры могли использовать один сервер Redis.

Для v0.1 предлагаю логический идентификатор `bridge_id = local`, который впоследствии можно заменить на идентификатор конкретного экземпляра плагина.

| Redis-ключ или канал                    | Назначение                   |
| --------------------------------------- | ---------------------------- |
| `se2:local:grids`                       | Список гридов                |
| `se2:local:grid:<grid_id>:gridinfo`     | Телеметрия грида и устройств |
| `se2.local.commands.device.<device_id>` | Команды конкретному блоку    |
| `se2:local:commands:ack`                | Подтверждения команд         |
| `se2:local:runtime:heartbeat`           | Доступность плагина          |

### Пример информации о гриде

```

{
  "schemaVersion": 1,
  "grids": [
    {
      "id": "123456",
      "name": "Scout-01",
      "isStatic": false,
      "deviceCount": 2
    },
    {
      "id": "789012",
      "name": "Base-01",
      "isStatic": true,
      "deviceCount": 4
    }
  ]
}

```

### Пример светильника

```

{
  "deviceId": "987654",
  "gridId": "123456",
  "deviceType": "lamp",
  "name": "Interior Light 1",
  "telemetry": {
    "enabled": true
  }
}

```

Это предлагаемые схемы сообщений, а не уже существующая телеметрия SE2. Идентификаторы приведены для примера. На первом этапе важно выяснить их настоящий тип и устойчивость при сохранении и загрузке мира.

### Управление из Python

Существующий `LampDevice` отправляет команды с именами `enable` и `disable`. Поэтому предлагаю сохранить такой формат:

```
import jsonimport uuidimport redisr = redis.Redis(    host="localhost",    port=6379,    decode_responses=True)device_id = "987654"grid_id = "123456"request_id = str(uuid.uuid4())r.publish(    f"se2.local.commands.device.{device_id}",    json.dumps({        "cmd": "enable",        "requestId": request_id,        "targetId": device_id,        "gridId": grid_id    }))print("Команда отправлена:", request_id)# Отправка не означает, что блок включился.# Результат следует проверить по ACK и телеметрии.
```

Плагин должен возвращать подтверждение с тем же `requestId`, например:

```
{
  "requestId": "example-request-001",
  "status": "confirmed",
  "deviceId": "987654",
  "actualState": {
    "enabled": true
  }
}
```

В реальной работе значения `requestId` должны совпадать. Статус `confirmed` допускается только после повторного чтения состояния блока, а не просто после получения сообщения из Redis.

## 5. Технические правила первой версии

Предлагаю сразу зафиксировать несколько ограничений, чтобы не повторять ошибки из SE1.

- Никаких игровых операций из потока Redis. Команды ставятся в очередь и исполняются в допустимом потоке игры.
- Не полагаться на имена блоков. Основной ключ — идентификатор устройства плюс идентификатор грида. Совпадающие имена не должны мешать управлению.
- Не считать `Redis publish = 1` успешной командой. Это только факт наличия подписчика.
- Не мешать работе игры при недоступности Redis. Сетевые ошибки обрабатываются отдельно, без блокировки игрового цикла.
- Не открывать произвольное выполнение C# через Redis. Только разрешённые команды, проверка формата и прав управления. Для удалённого Redis — аутентификация и защищённое соединение.

Начальные интервалы предлагаю такие: полный поиск гридов раз в 2–5 секунд, телеметрия светильников раз в 500 мс или при изменениях. После первого запуска измерим нагрузку и при необходимости скорректируем.

## 6. Критерии завершения v0.1

Приёмка SE2 Redis Bridge v0.1

0 / 8

SE2 запускается с плагином Pulsar без ошибок.

В Redis появляется список минимум двух тестовых гридов.

Для выбранного грида доступны идентификаторы и имена светильников.

Python включает выбранный светильник, не затрагивая соседний.

Python выключает этот светильник и получает подтверждение.

Изменение состояния вручную в игре отражается в Redis.

Создание или удаление блока обновляет список устройств.

После перезапуска игры и Redis плагин восстанавливает корректную работу.

В первой версии не реализуем управление двигателями, гироскопами, инвентарями, физикой, программируемые блоки и поддержку произвольных мультиплеерных серверов.

На первых этапах `SeMcp2` можно использовать как исследовательский инструмент, но конечный плагин должен работать самостоятельно. Зависимость от `SeMcp2` в релизе нам не нужна.

Моё предложение: считать v0.1 завершённой, когда мы сможем с другого Python-процесса получить список гридов, найти светильник и реально включить/выключить его с подтверждением состояния.

Это небольшая, проверяемая задача. После её выполнения добавление следующего устройства в основном сведётся к созданию нового C#-адаптера и описанию его команд — без переработки всей Redis-инфраструктуры.
