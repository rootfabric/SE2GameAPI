# Устройства SE2, версия 0.0.5

## Поток работы

`Python → RedisGateway → CommandRouter → DeviceAdapter → наблюдение состояния → ACK`.

Один `DeviceBridge` запускает работу в серверной DCS-сцене каждые 50 мс. Он передаёт
один `SceneBudget` (мягкий предел 0,5 мс) реестру, маршрутизатору и телеметрии.
Порядок фаз циклически меняется: загрузка команд не должна навсегда вытеснять чтение
состояний или обнаружение новых блоков. Отдельных таймеров на устройства нет.

## Классы устройств

- `DeviceAdapter`: идентификатор, чтение снимка, применение команды с возвратом
  предиката подтверждения. Подходит также для устройств без переключателя питания.
- `FunctionalDevice`: адаптер PowerableBlockComponent. Общие enabled, working,
  functional, имена, revision; команды enable/disable/set_enabled/toggle и SE1-алиасы
  on/off/start/stop. Смена времени измерения не увеличивает revision.
- `LampDevice`: наследует общий переключатель без дублирования кода.
- `DoorDevice`: наследует переключатель, добавляет open/close/toggle_door,
  наблюдает Open/Closed/Opening/Closing. ACK открытия означает конечное Open,
  а не принятие запроса на движение. Неработающая дверь отклоняет операцию.

`toggle` всегда переключает питание, `toggle_door` — положение двери. Это устраняет
неоднозначность между базовым обработчиком и обработчиком двери в SE1.

Специфические свойства — неизменяемый record в `DeviceState.Properties`:
у двери `{status, isOpen}`. Новые адаптеры добавляют свои DTO, не расширяя центральный
switch или формат снимка. Только DTO со значениями: передавать игровые объекты,
ленивые перечисления или изменяемые коллекции фоновому сериализатору запрещено.
Capabilities явно объявляют доступные операции; сейчас switch.enabled и door.open.
Сложные параметры будущих команд потребуют типизированного payload и проверки
типов, единиц, диапазонов в адаптере до записи в игру.

Для добавления типа:

1. Наследовать DeviceAdapter либо FunctionalDevice.
2. Реализовать чтение специфического DTO, Apply и проверку фактического результата.
3. Добавить распознавание компонента в DeviceFactory. Общие команды делегировать base.
4. Добавить Python-подкласс и регистрацию в Client.devices, тест фактического состояния.

## Ограничение нагрузки

- До 64 незавершённых запросов транспорта, до 16 допусков/обслуживаний очередей за проход.
- Очередь каждого устройства: до 8 ожидающих плюс одна исполняемая команда.
  Переполнение возвращает target_busy; медленная дверь не блокирует очередь лампы.
- Подтверждения имеют тот же бюджет, что и команды. Пока команда не подтверждена
  или не истёк deadline, следующая команда этому устройству не применяется.
- Поиск: список гридов раз в 5 секунд, блоки — порциями до 128 за проход,
  до 32 слотов одного грида. Version хранилища перезапускает курсор после изменений.
  Span и итераторы игрового API не сохраняются между проходами.
- Телеметрия: до 64 устройств за проход, целевая частота полного снимка 5 Гц.
  Каждый объект имеет собственное measuredAtMs, публикация не делает старые данные свежими.
- JSON, Redis, файлы и дедупликация — фоновая работа. Кэш дедупликации ограничен
  4096 результатами на 60 секунд; исчерпание явно возвращает dedup_capacity.
  Уже выполненные операции не вытесняются из кэша ради новых команд.
- Никакой гарантии exactly-once после краша; тайм-аут после применения — неизвестный
  исход, требуется чтение состояния. Deadline не отменяет начавшееся движение двери.

## Практические пределы

0,5 мс — кооперативный бюджет, а не жёсткий предел: одиночный вызов API, JIT/GC,
создание массива снимка и получение списка гридов нельзя прервать. На больших мирах
нужны дополнительные измерения. Публикуется полный снимок, подписки по интересу и
дельта-телеметрия пока не реализованы. Лимит нагрузки защищает сценовую работу ценой
снижения частоты телеметрии/роста задержки; гарантии real-time для любого числа
внешних программ нет. Авторизация, владение устройствами и приоритеты клиентов —
отдельный следующий слой, текущий стенд доверенный и локальный.

## Проверки

`tests/SchedulerTests`: реальный CommandRouter с подставными игровыми адаптерами —
изоляция долгой операции, последовательность одного устройства, deadline/epoch,
переполнение, сброс сессии, удаление устройства.

`tests/live_devices.py`: два типа устройств в игре, общие команды, открытие/закрытие,
одновременная работа двери и лампы, revision, нагрузка, восстановление и сравнение
исходных состояний всех устройств. Отчёт: devices-test-2026-11-09.json.

`tests/live_redis_lamps.py`: прежние сценарии ламп, дубль toggle, ошибочные адреса,
конфликты revision, отключение и восстановление Redis.
